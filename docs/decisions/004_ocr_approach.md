# ADR-004: 画像読み取りに OpenCV + Tesseract（ローカル）を採用する

## ステータス

採用（数値は桁テンプレート照合に変更済み。ユーザ名も前処理の見直しで目標達成）

## 背景

PRD の制約として、画像の読み取りはローカルで完結させる（外部サービスへ画像を送らない）。読み取り対象は、日本語・英数字が混在するユーザ名と、カンマ区切りの数値（レベル・名誉）。目標正答率は初期 70%。

## 決定内容

- メンバーカードの位置は、OpenCV によるアイコン（剣）のテンプレートマッチングで検出し、アイコン基準の相対比率で名前・数値の領域を切り出す。
- 文字認識は Tesseract 5（`jpn` / `eng`）を使い、`OcrEngine` インターフェース越しに呼び出す。
- 精度が目標に届かない場合は、`OcrEngine` の別実装（例: EasyOCR、PaddleOCR などローカルで動くもの）に差し替える。

## 理由

| 候補 | 評価 | 採否 |
|---|---|---|
| OpenCV + Tesseract | ローカル完結。導入が容易で、数値領域は文字種の制限（ホワイトリスト）で精度を上げやすい。ユーザ名の装飾フォントへの精度は未検証 | 採用（初期） |
| EasyOCR / PaddleOCR 等 | 精度が高い可能性があるが、深層学習の依存（容量・Python バージョン互換）が重い。必要になった場合の差し替え候補 | 保留 |
| 外部の画像認識 API | 画像が外部に送信されるため PRD の制約に反する | 却下 |
| 固定座標での切り出し | 端末・解像度・スクロール位置の違いに弱い | 却下 |

## 影響・トレードオフ

- 初期構成は軽量で、ローカル完結の要件を満たす。
- ユーザ名の誤読が多い可能性がある。「要確認」フラグ、類似名の検出、別名登録で運用上カバーする。
- Tesseract 本体は pip で導入できないため、環境構築手順に含める。
- 実装の最初に `scripts/evaluate_accuracy.py` で測定し、70% 未満なら差し替えを検討する。

## 追記（2026-11-22）: 数値は桁テンプレート照合で読む

サンプル 10 枚・31 人分で測定したところ、Tesseract は数値（レベル・名誉）でゲーム独自フォントの「4」を誤読し、「44」の並びで桁が落ちた（449,368→49368 など）。前処理（拡大率・psm・二値化・太さ）を 30 通り以上試しても解消しなかったため、数値のみ、1 桁ずつ切り出してテンプレート画像（`assets/digits/`）と照合する方式（`ocr/digit_reader.py`）に変更した。外部通信は行わず、ローカル完結の制約は守られる。テンプレートが使えない場合は従来の Tesseract にフォールバックする。ユーザ名は引き続き Tesseract で、精度は別途改善する。

## 追記（2026-11-23）: ユーザ名は前処理を「グレースケールのまま」に変更

ユーザ名の誤読は 9 人あった。名前領域の画像自体は鮮明で、原因は Otsu 二値化と 3 倍拡大が細い字を崩していたことだった。前処理を 30 通り以上比較し（拡大率 1〜3 倍、ぼかし、二値化の有無、文字範囲への切り詰め、psm 7/13）、拡大・二値化なしのグレースケールが最良（40 枚中 38 枚正解。従来は 31 枚）だった。拡大率 1.5 倍＋ぼかしでも 37 枚と同傾向のため、特定の値への過学習ではない。

結果、サンプル 10 枚・31 人分の正答率は 91.4%（85/93 項目）で、目標 70% を達成した（EasyOCR 等への差し替えは不要と判断）。残る誤りは、半濁点を濁点と誤読した名前（例: 「ぽこた」→「ぼこた」）と、難読漢字を含む長い名前の 2 人と、古い時点のスクリーンショットにある 1 人の値違い。なお半濁点の誤読は、誤読でも信頼度が高く、「要確認」にならない。類似名検出（`similar_to`）による運用でカバーする。

## 追記（2026-11-23）: 名前は 2 つの Tesseract モデルで読み、食い違いを「要確認」にする

別日の画像 12 枚・36 人分（元解像度）で汎化を確認したところ、数値は全件正解だったが、名前は 4 件を誤読した（半濁点の誤読、短い名前、難読漢字）。誤読のうち 2 件は信頼度が高く、「要確認」にならなかった。

Tesseract のパラメータ（psm 6/8/13、辞書の無効化、言語、拡大率、CLAHE）を比べたが、改善しなかった。一方、高精度モデル（`tessdata_best` の `jpn` / `eng`、約 30MB）は、従来モデル（`tessdata_fast` 相当、約 2.4MB の `jpn`）が誤読する名前を読めるものの、別の名前（下線を含む名前）で新たな誤読を出した。誤読する名前がモデルごとに異なるため、**2 モデルで読み、結果を突き合わせる**方式にした。

- 従来モデル（グレースケール）と高精度モデル（濃淡を引き伸ばしたグレースケール）の両方で名前を読む
- 信頼度が高い方を採用する。2 つの結果が（空白・全角半角・大文字小文字を無視して）食い違う場合は、採用した結果の信頼度を `NAME_DISAGREE_CONFIDENCE_CAP`（既定 55）以下にして「要確認」にする
- 高精度モデルの学習データが `assets/tessdata_best/` に無い場合は、従来どおり 1 モデルで読む（学習データは git 管理外。取得手順は `docs/setup.md`。Tesseract のネイティブコードが読むファイルなので、コミットを固定して SHA-256 を検証する）
- 学習データが壊れていると全画像が失敗扱いになるため、エンジン初期化時に試し読みで検証する

結果（88 カード分の名前）: 正解 82 → 85、「信頼度が高いのに誤り」 3 種 → 0。誤りは全て「要確認」になる。項目単位の正答率は、サンプル 10 枚が 91.4% → 94.6%、別日 12 枚が 88.9% → 94.4%。代償として、正しく読めた名前のうち「要確認」になるものが増える（4 → 7 カード）。名前の読み取りは 1 カードあたり Tesseract を 2 回呼ぶため、取り込みは遅くなる。

残る誤りは、難読漢字を含む長い名前と、下線を含む名前（`おはる_oharu` が `おはる._oharu` になる）。
